# Hand-rolled session auth for the FastAPI window: argon2, Postgres sessions, invites, CSRF

Everything a closed-registration email+password login for the window needs exists as primary-sourced, small pieces; nothing requires a framework. **The concrete assembly**: `argon2-cffi==25.1.0` with `PasswordHasher()` stock defaults (the RFC 9106 second recommended option - t=3, 64 MiB, p=4 - which exceeds every minimum row in the current OWASP Password Storage Cheat Sheet) plus the documented verify-then-`check_needs_rehash` login flow; sessions as `secrets.token_urlsafe(32)` (256 bits, 4x OWASP's 64-bit session-ID floor) stored in Postgres as a SHA-256 digest with the cookie set `Secure; HttpOnly; SameSite=Lax; Path=/` under a `__Host-` prefix (Starlette's `set_cookie` defaults `secure=False, httponly=False` - both must be set explicitly); idle and absolute expiry enforced in the `WHERE` clause at read time because Postgres has no row TTL; a new token minted on every login (Django's `cycle_key` precedent) and the row deleted on logout (OWASP: server-side invalidation is "mandatory"). Reset and invite tokens are the same generator feeding a separate single-use table - hashed at rest (GitLab's model; Django and fastapi-users store theirs plaintext, so hashing is strictly stronger than the mainstream), ~1 h TTL for reset (fastapi-users' default 3600 s) and 72 h for invites (Django's own `PASSWORD_RESET_TIMEOUT` default is exactly 3 days), consumed by setting `used_at` in the same transaction that acts. The invite flow is Django's shape with the documented trap avoided: admin creates the user with no password hash, the app mints the invite token directly, and the public forgot-password path deliberately excludes not-yet-activated users (Django's `PasswordResetForm.get_users` filters on `has_usable_password()` for this reason). Role gating is FastAPI's own documented pattern - a `get_current_user` dependency chained into a parameterized `require_role` callable-instance, attached router-wide via `APIRouter(dependencies=[...])`, with a custom exception handler turning "not logged in" into a 303 redirect carrying `?next=` (the exact behavior Starlette's `@requires(redirect=...)` implements). CSRF is the one thing neither FastAPI nor Starlette ships: `SameSite=Lax` already stops cross-site form POSTs in conforming browsers per RFC 6265bis, but both the spec and OWASP say that is defense in depth, not the defense - since sessions are server-side anyway, OWASP's answer is the synchronizer token pattern: a per-session token stored in the session row, emitted as a hidden form field, compared with `secrets.compare_digest`.

All web sources fetched 2026-09-12.

## A. Passwords: argon2-cffi 25.1.0, stock defaults, verify-and-rehash

- **Pin `argon2-cffi==25.1.0`** - latest on PyPI, `requires_python >=3.8`, classifiers through 3.14 (https://pypi.org/pypi/argon2-cffi/json), so the window's Python 3.9 venv is in range. Released 2025-06-03; the release dropped 3.7 (https://raw.githubusercontent.com/hynek/argon2-cffi/main/CHANGELOG.md).
- **Defaults are already right.** `argon2.PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4, hash_len=32, salt_len=16, type=Type.ID)` - "Uses Argon2id by default and uses a random salt for hashing"; the defaults "are taken from argon2.profiles.RFC_9106_LOW_MEMORY" (https://argon2-cffi.readthedocs.io/en/stable/api.html), adopted in 21.2.0 per the changelog. `argon2.profiles` ships `RFC_9106_HIGH_MEMORY` (t=1, m=2 GiB, p=4) and `RFC_9106_LOW_MEMORY` (t=3, m=64 MiB, p=4) matching RFC 9106 §4's FIRST and SECOND RECOMMENDED options verbatim ("Argon2id with t=3 iterations, p=4 lanes, m=2^(16) (64 MiB of RAM), 128-bit salt, and 256-bit tag size. This is the SECOND RECOMMENDED option." - https://www.rfc-editor.org/rfc/rfc9106.html), and the RFC makes Argon2id the MUST-support variant.
- **OWASP's floor is far below the library default.** Password Storage Cheat Sheet: "Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism," with an equal-defense table from m=47104/t=1/p=1 down to m=7168/t=5/p=1, then scrypt (2^17), bcrypt (work factor >= 10, 72-byte limit), PBKDF2-HMAC-SHA-256 600 000 for FIPS (https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Conclusion: do not hand-tune parameters; the stock `PasswordHasher()` satisfies OWASP and RFC 9106 simultaneously. The docs' own advice: "You can probably just use argon2.PasswordHasher with its default values and be fine" (~50 ms per hash), and `python -m argon2 --profile` benchmarks on the target box (https://argon2-cffi.readthedocs.io/en/stable/parameters.html).
- **The login flow is documented, not invented.** `verify(hash, password)` returns True or raises - `VerifyMismatchError` (wrong password), `VerificationError`, `InvalidHashError` - and parses salt and parameters out of the encoded hash itself; `check_needs_rehash(hash)` returns whether the hash was made with the instance's current parameters, checked "whenever a user logs in" (https://argon2-cffi.readthedocs.io/en/stable/api.html). The usage page's canonical `login()` is exactly: verify, then `if ph.check_needs_rehash(hash): db.set_password_hash_for_user(user, ph.hash(password))` (https://argon2-cffi.readthedocs.io/en/stable/howto.html). Exceptions-not-booleans is a deliberate design ("Errors should never pass silently" - https://argon2-cffi.readthedocs.io/en/stable/faq.html). The final comparison in the wrapped C library is constant-time (`argon2_compare`'s XOR-accumulate loop in https://raw.githubusercontent.com/P-H-C/phc-winner-argon2/master/src/argon2.c).
- **Threading**: the FAQ answers "Does argon2-cffi release the GIL?" with, in full, "Yes." So hashing in a worker thread doesn't block the event loop - in FastAPI that means either plain `def` route handlers (FastAPI runs those in its threadpool) or `run_in_threadpool` from async ones; never `ph.verify` inline in an `async def`, since each call burns ~50 ms CPU and allocates the full 64 MiB `memory_cost` for its duration.

## B. Sessions: opaque token, hashed row in Postgres, strict cookie flags

**Token.** `secrets.token_urlsafe(32)` - pass the 32 explicitly: `DEFAULT_ENTROPY` is 32 bytes today (CPython `Lib/secrets.py`) but the docs say "The exact value is subject to change at any time, including during maintenance releases" (https://docs.python.org/3/library/secrets.html). The docs' own sizing guidance: "As of 2015, it is believed that 32 bytes (256 bits) of randomness is sufficient for the typical use-case expected for the secrets module." OWASP's session floor is 64 bits ("Session identifiers must have at least 64 bits of entropy" - https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), so 256 bits clears it 4x. The ID must be opaque: "The session ID content (or value) must be meaningless" with all meaning "stored on the server side... in a session management database or repository" - which is precisely the argument against Starlette's `SessionMiddleware`: its source signs `b64encode(json.dumps(session))` with `itsdangerous.TimestampSigner` and keeps no server record (https://raw.githubusercontent.com/encode/starlette/master/starlette/middleware/sessions.py) - readable client-side, and nothing to revoke. A revocable session is a Postgres row, not a signed cookie.

**Hash at rest.** Store `sha256(token)` hex as the indexed lookup column, never the raw token. Primary-source status honestly: the OWASP session sheet never requires hashing stored session IDs (its only hashing mention is for logs), and the two mainstream Python references store session keys plaintext - Django's `Session.session_key` is `get_random_string(32, a-z0-9)` (~165 bits) stored as-is as the PK (https://github.com/django/django/blob/stable/6.1.x/django/contrib/sessions/backends/base.py), and fastapi-users' `DatabaseStrategy` makes the raw `secrets.token_urlsafe()` the PK, `String(length=43)` (https://github.com/fastapi-users/fastapi-users-db-sqlalchemy/blob/main/fastapi_users_db_sqlalchemy/access_token.py). The hashed-at-rest precedents are django-rest-knox (default `hashlib.sha512` of a 64-hex-char token - https://raw.githubusercontent.com/jazzband/django-rest-knox/develop/knox/crypto.py) and GitLab (SHA-256 with an instance salt - https://gitlab.com/gitlab-org/gitlab/-/raw/master/lib/gitlab/crypto_helper.rb). A fast hash is enough here because slow hashes exist to compensate for low-entropy human passwords (the OWASP SHA-256 prohibition is explicitly scoped to password storage); a 256-bit random token is not brute-forceable at any hash speed, and hashing costs one line while turning a leaked `sessions` table into garbage. Lookup is indexed equality on the digest - no `compare_digest` needed on the DB path, since an attacker can't produce the digest without the token.

**Cookie.** Per RFC 6265bis (draft-22, 2025-12-01, in the RFC Editor queue - https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html): `Secure` limits the cookie to "a secure channel"; `HttpOnly` omits it "via non-HTTP APIs"; `__Host-` requires `Secure`, `Path=/`, and no `Domain` (§4.1.3.2) - OWASP: "Recommended for session IDs." Set SameSite explicitly - unspecified defaults to a browser-discretion "Lax-allowing-unsafe" mode (§5.6.7.2). OWASP wants "SameSite=Strict (preferred) or SameSite=Lax"; Lax is right for this app because a link into `/history` from an email or issue should arrive logged in (Strict strips the cookie from cross-site top-level navigations too). Starlette's `Response.set_cookie` defaults `samesite="lax"` but `secure=False, httponly=False` (https://raw.githubusercontent.com/encode/starlette/master/starlette/responses.py) - so every flag except samesite is on the caller. `delete_cookie` is `set_cookie` with `max_age=0` and must repeat the same path/secure/samesite or the deletion won't match.

**The loopback bind is not an obstacle to `Secure`.** The browser judges `Secure`/`__Host-` against the browser-facing scheme (https at the front proxy), not the app's `127.0.0.1` HTTP bind (`deploy/systemd/tracewake-web.service` runs `uvicorn app:app --host 127.0.0.1`). What the app does need is a correct `request.url.scheme` for redirects and `url_for`: uvicorn's `--proxy-headers` is "Defaults to enabled, but is restricted to only trusting connecting IPs in the forwarded-allow-ips configuration," and `forwarded-allow-ips` defaults to `127.0.0.1` and `::1` (https://raw.githubusercontent.com/encode/uvicorn/master/docs/settings.md) - so a same-host proxy sending `X-Forwarded-Proto: https` (the deployment docs' sample nginx line) already flips `scope["scheme"]` via uvicorn's `ProxyHeadersMiddleware` (https://raw.githubusercontent.com/encode/uvicorn/master/uvicorn/middleware/proxy_headers.py) with zero configuration.

**Expiry and rotation.**

- OWASP ranges: idle "15-30 minutes for low risk applications" (2-5 for high-value); absolute "between 4 and 8 hours" - though see the fit section for why this app can defensibly run longer.
- Postgres has no TTL, so the session query enforces both bounds itself - `WHERE token_hash = %s AND created_at > now() - interval '12 hours' AND last_seen_at > now() - interval '30 minutes'` - plus a periodic `DELETE` sweep for hygiene. `now()` is transaction-start time and constant within the transaction (https://www.postgresql.org/docs/current/functions-datetime.html); `timestamptz` stores UTC internally (https://www.postgresql.org/docs/current/datatype-datetime.html). Deriving absolute expiry from `created_at` at read time (fastapi-users' `max_age` pattern in `strategy/db/strategy.py`) beats a stored `expires_at` - one fewer column to keep consistent.
- Rotation: OWASP - "The session ID must be renewed or regenerated by the web application after any privilege level change," login being "the most common scenario where the session ID regeneration is mandatory." Django implements this as `cycle_key()` inside `login()` - new key, data copied, old row deleted - and flushes entirely if the session belonged to a different user (https://github.com/django/django/blob/stable/6.1.x/django/contrib/auth/__init__.py). Hand-rolled equivalent: on successful login, insert a fresh row, delete any row the presented cookie referenced, set the new cookie.
- Logout: OWASP - invalidation "on both sides, client and server. The latter is the most relevant and mandatory from a security perspective." `DELETE` the row; the cookie clear is a courtesy.

## C. Single-use tokens: one table for reset and invite

Two workable designs exist. The **stateless** one (no table): Django's `PasswordResetTokenGenerator` HMACs `{user.pk}{user.password}{last_login}{timestamp}{email}` under a key salt, so using the token changes the very state it was computed from - the docstring calls this "a token that is invalidated when it's used: password field changes upon reset, last_login updates shortly after" (https://github.com/django/django/blob/stable/6.1.x/django/contrib/auth/tokens.py). fastapi-users does the same idea inside a JWT: `forgot_password` embeds `"password_fgpt": self.password_helper.hash(user.hashed_password)` and `reset_password` refuses when the current stored hash no longer verifies against the fingerprint (https://github.com/fastapi-users/fastapi-users/blob/master/fastapi_users/manager.py). Elegant, zero storage - but single-use only indirectly, unrevocable individually, and it drags a signing secret into a codebase that otherwise has none.

The **stateful** design fits a raw-psycopg app better and is what the OWASP Forgot Password Cheat Sheet describes: tokens "Generated using a cryptographically secure random number generator... Linked to an individual user in the database. Invalidated after they have been used. Stored in a secure manner, as discussed in the Password Storage Cheat Sheet," plus "Single use and expire after an appropriate period" and rate limiting against URL-token brute force (https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Concretely:

- One `account_tokens` table: `user_id`, `purpose` (`'invite'` | `'reset'`), `token_hash` (SHA-256 of a `secrets.token_urlsafe(32)`), `created_at`, `expires_at`, `used_at`. Hashing at rest follows GitLab's invite model - `Devise.token_generator.generate` stores the digest and keeps the raw token in memory only long enough to email it (https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/models/member.rb); Discourse by contrast stores its short `SecureRandom.base58(10)` invite keys plaintext and leans on expiry (https://github.com/discourse/discourse/blob/main/app/models/invite.rb). Hash: the raw token exists only in the emailed URL.
- TTLs: OWASP gives no number ("appropriate period" is the exact wording), so borrow the two field-tested defaults: **reset ~1 h** - fastapi-users' `reset_password_token_lifetime_seconds: int = 3600` (manager.py); **invite 72 h** - Django's `PASSWORD_RESET_TIMEOUT = 60 * 60 * 24 * 3` ("Default: 259200 (3 days, in seconds)" - https://docs.djangoproject.com/en/6.1/ref/settings/#password-reset-timeout), the token Django's invite pattern actually rides on. Discourse's 90-day `invite_expiry_days` (https://github.com/discourse/discourse/blob/main/config/site_settings.yml) is the generous outlier; 72 h suits a two-role instance where the admin can trivially re-invite.
- Single-use enforcement: consume in the acting transaction - `UPDATE account_tokens SET used_at = now() WHERE token_hash = %s AND used_at IS NULL AND expires_at > now() RETURNING user_id, purpose`, and only proceed when a row comes back; the password write, token consumption, and (per OWASP session guidance) deletion of the user's other sessions commit together. `used_at IS NULL` in the `UPDATE` makes replay a no-op even under concurrent submits.
- New reset issuance invalidates prior unused reset tokens for that user (one live token per purpose) - the stateful analogue of the fingerprint trick.

## D. Invite flow: closed registration, Django's shape, Django's trap avoided

The window's registration is closed - the admin creates accounts. Django's canon, all source-verified:

- **Unactivated = no usable password.** `set_unusable_password()` stores `"!" + get_random_string(40)` - a value that can never verify (https://github.com/django/django/blob/stable/6.1.x/django/contrib/auth/base_user.py, hashers.py). The psycopg equivalent: `password_hash NULL` means invited-not-activated, and login refuses NULL before ever calling argon2.
- **The trap: don't route invitees through forgot-password.** Django's `PasswordResetForm.get_users` filters `if u.has_usable_password()`, and the docs state why: "Users flagged with an unusable password ... aren't allowed to request a password reset to prevent misuse when using an external authentication source" (https://github.com/django/django/blob/stable/6.1.x/django/contrib/auth/forms.py, https://docs.djangoproject.com/en/6.1/ref/contrib/auth/#django.contrib.auth.models.User.set_unusable_password). So the public reset form must exclude never-activated accounts too - it doubles as an account-exists oracle otherwise - and always answer the same "if that address exists, mail was sent" page.
- **The invite is a directly minted token, not a reset request.** Django's `make_token`/`check_token` have no usable-password check - admin code mints the token itself and emails the link. Hand-rolled: `POST /admin/users` inserts the user row (email, role, `password_hash NULL`), inserts an `'invite'` token row at 72 h, emails `/invite/{token}`. The landing `GET` shows a set-password form only when the token row is live; the `POST` sets the argon2 hash, stamps `used_at`, and (sensibly) logs the new user straight into a fresh session.
- Reset and invite then share one code path: same table, same set-password form, different `purpose`, different TTL, and reset additionally requires the account to be activated.

## E. Role gating: dependencies all the way, 303 to login for HTML

Two roles (admin, reader) map onto FastAPI's documented dependency chain - every piece below is from FastAPI's own docs or Starlette source, though note the redirect recipe as a whole is composed, not copied from a single official example:

- `get_current_user(request)` - read the cookie, hash it, one indexed `SELECT` joining `sessions` to `users` with the expiry predicates from §B, update `last_seen_at`, return the user row; raise on failure. This is the tutorial's `get_current_user` shape (https://fastapi.tiangolo.com/tutorial/security/get-current-user/), and chaining a stricter dependency on top of it is the docs' own framing ("we create an additional dependency get_current_active_user that in turn uses get_current_user").
- `require_role("admin")` - the callable-instance pattern from https://fastapi.tiangolo.com/advanced/advanced-dependencies/ (a class with `__init__(self, role)` and `__call__(self, user = Depends(get_current_user))`, used as `Depends(require_admin)`); the docs note FastAPI's own security utilities use this same pattern. Wrong role raises 403 - the 401-vs-403 split (missing auth vs insufficient auth) is how the security tutorial and fastapi-users' `Authenticator` both draw it.
- **Whole-router gating covers the POSTs for free.** `APIRouter(dependencies=[Depends(require_admin)])`: "All these path operations will have the list of dependencies evaluated/executed before them," return values discarded, router deps running before decorator deps (https://fastapi.tiangolo.com/tutorial/bigger-applications/); per-route `dependencies=[Depends(...)]` in the decorator does the same for one endpoint (https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-in-path-operation-decorators/). An `admin` router (user management, invites) and a `reader`-gated everything-else router split the app cleanly.
- **HTML wants a redirect, not a 401 page.** The idiom: `get_current_user` raises a custom `NotAuthenticated` exception, and an `@app.exception_handler(NotAuthenticated)` returns `RedirectResponse(f"/login?{urlencode({'next': str(request.url)})}", status_code=303)` - custom exception handlers returning arbitrary responses are documented at https://fastapi.tiangolo.com/tutorial/handling-errors/. This mirrors what Starlette's own `@requires(scopes, redirect="login")` does in source: on failure it builds `url_for(redirect)` with `?next=<original url>` and returns `RedirectResponse(..., status_code=303)`, for POSTs as well as GETs (https://raw.githubusercontent.com/encode/starlette/master/starlette/authentication.py). Keep 403 (wrong role) as a plain rendered page - redirecting an authenticated reader to login is wrong.
- **Redirect status codes**: Starlette's `RedirectResponse` defaults to **307** (source: `status_code: int = 307`), which per RFC 9110 §15.4.8 "MUST NOT change the request method" - a 307 after a login POST replays the POST at the target. Use **303 See Other** after every form POST ("the user agent ought to retrieve the target resource using GET" - RFC 9110 §15.4.4, https://www.rfc-editor.org/rfc/rfc9110.html). Validate `next` as a same-origin path (leading `/`, no scheme/host) before redirecting into it.

## F. CSRF: nothing built in; synchronizer token in the session row

- **Confirmed absence.** Starlette's middleware page lists CORS, Session, HTTPSRedirect, TrustedHost, RequestBodyLimit, GZip, BaseHTTPMiddleware - no CSRF; CSRF appears only under third-party middleware (simonw/asgi-csrf, frankie567/starlette-csrf) (https://raw.githubusercontent.com/encode/starlette/master/docs/middleware.md). FastAPI's sole CSRF-titled feature, strict Content-Type checking (0.132.0, https://fastapi.tiangolo.com/advanced/strict-content-type/), covers only credential-less `fetch()` against unauthenticated localhost apps - it does nothing for cookie-authenticated form POSTs.
- **SameSite=Lax is real but not sufficient by the sources' own words.** RFC 6265bis: a Lax cookie rides a cross-site request only for a top-level navigation with a safe method (§5.8.3), so a cross-site `<form method=POST>` never carries it in a conforming browser - and the same spec immediately hedges that Lax "provides reasonable defense in depth against CSRF attacks that rely on unsafe HTTP methods... but does not offer a robust defense against CSRF as a general category of attack" (§5.6.7.1). OWASP: "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments," carving out a SameSite-only exception gated on five conditions (fully controlled registrable domain, zero state-changing safe-method endpoints, Strict or Lax+`__Host-`, Origin/Referer verification in place, accepting non-enforcing browsers) and otherwise requiring a token pattern (https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). This app on its own subdomain arguably passes the five conditions - but the token costs a dozen lines, so take the layered posture.
- **The right pattern here is the synchronizer token, because sessions are already server-side.** OWASP's hierarchy: framework protection first; "Stateful software should use the synchronizer token pattern. Stateless software should use double submit cookies" (signed double-submit "(RECOMMENDED)", naive "(DISCOURAGED)"). The signed double-submit exists precisely to avoid server-side state - state this app has. Implementation: a `csrf_token` column (`secrets.token_urlsafe(32)`) in the session row, minted with the session and rotated with it; templates emit `<input type="hidden" name="csrf_token" value="...">`; a shared check on every POST compares the form value against the session's with `secrets.compare_digest` (constant-time per https://docs.python.org/3/library/secrets.html) and 403s on mismatch. HTMX-driven POSTs, if any arrive later, carry the same value via a header (`hx-headers` on `<body>`), matching OWASP's custom-request-header note for AJAX.
- Defense in depth worth its three lines: reject unsafe methods when `Sec-Fetch-Site: cross-site` - OWASP now calls Sec-Fetch-Site "the primary signal for CSRF protection" with Origin-header fallback for pre-2023 browsers.
- The off-the-shelf options fit poorly: starlette-csrf v3.0.0 (2024-07-24, quiet since) validates a signed cookie against the `x-csrftoken` **header only** - plain HTML forms can't send it without JS - and signs a random value rather than binding the session ID (https://raw.githubusercontent.com/frankie567/starlette-csrf/main/starlette_csrf/middleware.py); asgi-csrf does accept a hidden field but implements double-submit, the stateless pattern this app doesn't need. Hand-rolling the synchronizer token is less code than integrating either.

## G. What fastapi-users is worth (and the version pins)

fastapi-users v15.0.5 (2026-03-27) is ORM-coupled and not adoptable wholesale, but three of its designs transfer directly, plus the pins:

1. **`verify_and_update` as the one password API** (fastapi_users/password.py): `PasswordHash((Argon2Hasher(), BcryptHasher()))` - argon2 for new hashes, bcrypt still verifiable - and `verify_and_update(plain, hashed) -> tuple[bool, str | None]`, where a non-None second element is the caller's cue to write back a rehash. Same contract as argon2-cffi's verify + `check_needs_rehash`, folded into one call; a hand-rolled `verify_password` should return this tuple shape. It pins `pwdlib[argon2,bcrypt] ==0.3.1` exactly (pyproject.toml; pwdlib 0.3.1 is current on PyPI). For a greenfield app with no legacy bcrypt hashes, direct `argon2-cffi==25.1.0` is the smaller dependency; pwdlib earns its place only when migrating old hashes.
2. **DatabaseStrategy validates the whole session-table shape** - `secrets.token_urlsafe()` token, DB row per session, `created_at`-derived expiry at read time, `destroy_token` deletes the row for real logout - while its JWTStrategy documents its own weakness in an exception message: "A JWT can't be invalidated: it's valid until it expires." (fastapi_users/authentication/strategy/db/strategy.py, jwt.py). The one deviation worth making from it: hash the stored token (§B).
3. **The dependency factory** - `current_user(active=True, superuser=False)` returns a Depends-able, so route declarations carry the policy. The `makefun` runtime-signature machinery exists only to support multiple pluggable backends; with one backend, plain functions plus the callable-instance pattern (§E) give the same ergonomics.
4. **CookieTransport ships secure defaults** - `cookie_secure=True, cookie_httponly=True, cookie_samesite="lax"` (authentication/transport/cookie.py) - the flags §B specifies, and stricter than Django's own `SESSION_COOKIE_SECURE = False` default.

Django (6.1.x) is the deeper reference implementation: session-key generation with a collision check, `cycle_key` rotation on login, the stateless reset-token HMAC, the unusable-password sentinel, and the two calibration constants this design borrows (3-day reset window, 2-week `SESSION_COOKIE_AGE`).

**Pins for `web/requirements.txt`**: `argon2-cffi==25.1.0` is the only new runtime dependency the whole design needs - sessions, tokens, CSRF, and role gating are `secrets`, `hashlib`, and SQL on the already-pinned fastapi 0.128.8 / starlette 0.49.3 / psycopg 3.2.13.

## What the sources do not answer

1. **Whether a fast hash of a high-entropy token at rest is "secure storage."** OWASP's Forgot Password sheet points at the Password Storage sheet, whose SHA-256 prohibition is scoped to passwords; no OWASP sentence blesses SHA-256-for-random-tokens explicitly. The practice rests on the entropy argument plus Knox/GitLab precedent - and Django/fastapi-users not hashing at all.
2. **Numeric TTLs for reset tokens.** OWASP says only "an appropriate period"; 1 h and 72 h are borrowed defaults (fastapi-users, Django), not standards.
3. **Hashing session IDs at rest** - the OWASP session sheet requires it only for logs, and is silent on the session store itself.
4. **No official FastAPI recipe for redirect-on-unauthenticated.** The §E handler is a composition of documented pieces (custom exception handlers + RedirectResponse); Starlette's `@requires(redirect=...)` is the nearest first-party implementation.
5. **`Secure` cookies during local preview.** `lab-preview.sh` serves plain `http://127.0.0.1`; whether browsers treat loopback as trustworthy for Secure cookie storage was not checked against a spec here - the safe move is an env-driven `secure` flag that the preview path disables, defaulting on.
6. **starlette-csrf's maintenance status** - one release since mid-2024; listed in Starlette's docs but not obviously tended.
7. **Whether fastapi-users' plaintext token storage was a considered decision** - no comment in the source or docs either way.
8. **RFC 6265bis is still a draft** (draft-22, "Obsoletes: 6265 (if approved)") - browser behavior tracks it, but the citable RFC is not yet issued.
9. **This app's right idle timeout.** OWASP gives risk-tiered ranges; where a single-admin project dashboard falls in them is a judgment call, not a finding.

## Fit against tracewake

- **The database is already there and already private.** The Selector Journal's Postgres runs unix-socket-only with peer auth (`listen_addresses = ''`, ADR 0015, deploy/ansible/roles/tracewake_controller/tasks/main.yml); `users`, `sessions`, and `account_tokens` tables in that instance inherit the same posture, and the window already imports the Journal's module from `selector/` rather than opening its own SQL surface - auth queries should live beside it.
- **The deployment matches the assumptions.** `tracewake-web.service` binds uvicorn to `127.0.0.1`; uvicorn's default `forwarded-allow-ips` of `127.0.0.1` means the front proxy's `X-Forwarded-Proto` is honored with no flag changes. The `Secure`/`__Host-` cookie needs the env-toggle from open question 5 for `lab-preview.sh`.
- **Python 3.9 is the venv floor** (app.py's `from __future__ import annotations` comment); argon2-cffi 25.1.0 requires >= 3.8. No conflict, but the tuple-returning `verify_and_update` shape must stay `Tuple[bool, Optional[str]]`-annotated or under the future import.
- **Roles map onto existing vocabulary.** The SPEC already has an operator concept (labeler allowlist, review capacity); `admin` is the operator - user management, invites, anything that mutates - and `reader` is everyone else looking at the Queue Board and history. The current routes are read-only GETs, so the first shippable slice is: reader gate on the whole app, admin router for user management, CSRF wiring on the login form itself and on whatever POST arrives first.
- **HTMX today is GET-only** (`hx-get` swaps in `_history_live.html`, `_loop_live.html`), so CSRF costs nothing until a mutating control appears in the UI; when one does, the session-row synchronizer token is already minted and a `hx-headers` attribute on `<body>` carries it.
- **Timeout calibration**: OWASP's 4-8 h absolute ceiling reads as high-value-app guidance; Django's shipped default is 2 weeks. A defensible middle for a project dashboard: 30-minute idle, 12-hour absolute, sliding `last_seen_at`, with the admin able to delete session rows - the revocability that motivated server-side sessions in the first place.
