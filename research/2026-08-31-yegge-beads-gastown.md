# Yegge's stack: beads, Gas Town, Gas City

Beads (`bd`) is real, mature-ish, MIT, and is exactly what its pitch says: a dependency-aware graph issue tracker that agents query instead of reading markdown plan files, born from Yegge burning a 350k-line orchestrator whose two fatal flaws were Temporal and *plan-file-based orchestration* — he ended that experiment with "six hundred and five markdown plan files in varying stages of decay." Its storage is not JSONL-in-git any more: since the Dolt rewrite the source of truth is a versioned SQL database (embedded Dolt in-process by default), `.beads/issues.jsonl` is "an export for viewers and interchange, not the source of truth," and sync is `bd dolt push/pull` against `refs/dolt/data` on the git remote. Gas Town is the multi-agent orchestrator built on beads — Mayor, polecats, Witness, Deacon, Dogs, Refinery merge queue, 20-30 concurrent Claude Codes in tmux — and its entire architecture is machinery for problems the Loop does not have, because every one of them is created by parallelism and by agents authoring their own work. Gas City **does exist as a distinct project** (`gastownhall/gascity`, created 2026-02-22, v1.0.0 announced 2026-04-24, v1.4.1 as of 2026-08-15): Gas Town "torn apart and rewritten from the ground up as an SDK," written not by Yegge but by Julian Knutsen and Chris Sells. The one idea in the whole stack that genuinely challenges the Loop's model is beads' `discovered-from` edge — a durable channel for work an agent notices mid-task — because the Loop's Progress Log is deleted when the Run's work ends and its Proposal-Only Output gives discovered work nowhere durable to go. Everything else beads offers (cross-session memory, ready-work queries, compaction) solves the standing-many-session-project problem, which the Loop deliberately avoids by scoping a Run to one operator-authored task.

## A. Beads (`bd`)

### What it is

"Distributed graph issue tracker for AI agents, powered by Dolt... Beads provides a persistent, structured memory for coding agents. It replaces messy markdown plans with a dependency-aware graph, allowing agents to handle long-horizon tasks without losing context" (README). Canonical repo is `gastownhall/beads` (github.com/steveyegge/beads redirects there). MIT license. Single Go binary `bd`; also shipped as npm `@beads/bd`, Homebrew, and a PyPI MCP server (`beads-mcp`).

The origin story matters because it is a controlled experiment against the plan-file model. Yegge's `vibecoder` (Sep 2025) used markdown plans as its orchestration substrate; a month later he had 605 decaying plan files and ripped out "70 thousand lines of plan-management code." His description of the failure mode is precise: agents wake up fresh, find a phase in a plan, and declare "Oh wow, this is a big project, I'm going to break it into five phases and create a markdown plan" — recursively, until "you have literally hundreds of new markdown files, all with low-context titles like `cleanup-tech-debt-plan-phase-4.md` — all partly implemented, all partly obsolete, all 100% useless." The fix, on 2025-10-08: "Screw it. Let's just move all known work from the plans into an issue tracker." ("Introducing Beads", 2025-10-13.)

Two claims from that post worth keeping verbatim because they are the load-bearing arguments:

- The session-boundary claim: "Beads manages to help with this problem, because you can just kill your agents after completing each issue. Beads helps agents easily find where they're supposed to pick up again, so it's easy to make your sessions throwaway." — i.e. beads independently arrives at the Ralph/Loop conclusion that the fresh process per task is the point, and positions itself as the state layer that makes it work.
- The discovered-work claim: "when you're using Beads, instead your agents will say, 'I notice all your tests are broken, by someone else, and I've filed issue 397 to get them working again,' and then they continue happily working... you'll never lose track of work items again."

### Data model (read from the schema, not the pitch)

Storage is a Dolt (MySQL-dialect, git-semantics) database; 128 migration files in `internal/storage/schema/migrations/`. The core tables:

- **`issues`** (migration 0001, since widened): `id` (hash-based, e.g. `bd-a1b2`, hierarchical children `bd-a3f8.1`), `title`, and four separate long-text fields — `description`, `design`, `acceptance_criteria`, `notes` — plus `status`, `priority` (int, P0-P4 style), `issue_type`, `assignee`, `estimated_minutes`, audit fields (`created_by`, `owner`, `closed_by_session`, `close_reason`), `external_ref`, compaction bookkeeping (`compaction_level`, `compacted_at`, `original_size`), messaging fields (`sender`, `ephemeral`), and a large tail of Gas-Town-era orchestration columns (`hook_bead`, `role_bead`, `agent_state`, `rig`, `await_type`, `waiters`, `defer_until`, `due_at`, `work_type`). The `acceptance_criteria` column being first-class in an issue tracker built *for agents* is notable — it is the same conclusion the Loop's Loud Skip encodes (a task without acceptance criteria is not workable).
- **`dependencies`**: `(issue_id, depends_on_id, type)` edges. 19 built-in edge types in `internal/types/types.go`, in four families: workflow (`blocks`, `parent-child`, `conditional-blocks`, `waits-for` — only these four affect readiness), association (`related`, `discovered-from`), graph links (`replies-to`, `relates-to`, `duplicates`, `supersedes`), and entity/audit edges (`authored-by`, `assigned-to`, `approved-by`, `attests`, `tracks`, `until`, `caused-by`, `validates`, `delegated-from`). Custom string types are allowed.
- **`ready_issues`** view (migration 0017/0025): a recursive SQL view — open, non-ephemeral, not past a `defer_until`, with no open `blocks` dependency directly or transitively through `parent-child` (depth-capped at 50). This is the whole "auto-ready task detection" feature: readiness is a database view, not agent judgment. It is structurally the same predicate as the Loop's Eligibility, computed in SQL instead of in the Selector.
- **Statuses**: `open`, `in_progress`, `blocked`, `deferred`, `closed`, `pinned` (persistent never-closing beads — identities, hooks), `hooked` (claimed by a worker). Issue types: bug/feature/task/epic/chore/decision/message/spike/story/milestone plus internal `molecule`, `gate`, `event`.
- **`bd_events_journal`** (migration 0064): an append-only, gapless, commit-ordered journal of every mutation, written in the same transaction as the mutation, deliberately clone-local (dolt-ignored, never replicated). Its 100-line SQL comment is the most carefully reasoned artifact in the repo. Beads independently reinvented the Selector Journal's shape: an append-only event record beside the tracker, read by tooling and by nothing that decides work.
- **Wisps** (migrations 0019-0021): ephemeral beads that live in the database but are never persisted to history — "the vapor phase of matter for Gas Town work" — used for orchestration noise (patrols, per-run workflows), optionally squashed to a one-line digest at burn time.

IDs are hash-based specifically so parallel agents and diverged branches never collide ("Hash-based IDs (`bd-a1b2`) prevent merge collisions in multi-agent/multi-branch workflows") — a problem a one-worker Loop does not have.

### How agents query and update it

Pure CLI with `--json` everywhere; optionally an MCP server. The workflow `bd init` writes into `AGENTS.md` is five commands: `bd prime` (workflow context injection), `bd ready` (the view above), `bd show <id>`, `bd update <id> --claim` (atomic assignee + `in_progress`), `bd close <id>`. `bd setup claude|codex|factory|cursor|...` installs SessionStart hooks so `bd prime` runs at every session start — explicitly "to prevent agents from forgetting bd workflow after context compaction" (`bd prime` docs; ~1-2k tokens CLI mode, ~50 tokens MCP mode, overridable per-workspace via `.beads/PRIME.md`).

Two memory planes beyond issues:

- **`bd remember "insight"` / `bd recall` / `bd memories`** — keyed persistent project notes that `bd prime` injects into every session; the README's suggested agent instruction is blunt: "Use `bd remember` for persistent project memory; do not create MEMORY.md files." They are stored in the config table under a reserved namespace with their own merge class (auto-resolve on pull), i.e. convergence is part of what a memory *means* (`memoryops/doc.go`).
- **Compaction** — "semantic 'memory decay' summarizes old closed tasks to save context window": `bd admin compact --analyze` picks 30+-days-closed candidates, an agent writes the summary, `--apply` swaps it in, `bd restore` recovers the original from a snapshot or Dolt history.

The commit convention closes the loop in the other direction: issue IDs in commit messages let `bd doctor` "detect orphaned issues — work that was committed but the issue wasn't closed" by cross-referencing open issues against git history.

### Maturity and license

MIT. Created 2025-10-12; ~815k lines of Go in the working tree as of 2026-08-31; 26,754 stars, 1,807 forks, 818 open issues; latest release v1.2.2 (2026-08-15), pushed daily. Contributions are dominated by Yegge (4,796 commits vs 772 for the next contributor) and the code is by his own account unreviewed by its author: "I've never seen the code, and I never care to... it's 225k lines of Go code that tens of thousands of people are using every day" ("Welcome to Gas Town", 2026-01-01 — the tree has since more than tripled). The engineering apparatus is nonetheless real: 128 schema migrations with down-scripts, a schema-version skew guard at open time, per-database named-lock migration serialization, a pinned Dolt version with a documented upstream-regression rationale, CI lint contracts, release gates. The honest read: fast-moving, heavily agent-authored, structurally serious, one-person-centric. The Dolt dependency is the biggest operational commitment — the storage engine is a full MySQL-compatible versioned database, pinned at 2.2.0 because 2.3.0 shipped a regression that bricks a few percent of fresh databases (`docs/architecture/dolt.md`).

## B. Gas Town (`gt`)

### What it is and what problem it solves

"Multi-agent orchestration system... Instead of losing context when agents restart, Gas Town persists work state in git-backed hooks" (README). Yegge's framing: "I predicted someone would lash the Claude Code camels together into chariots... I've tamed them to where you can use 20-30 at once, productively, on a sustained basis." It is his *fourth* orchestrator of 2025 (v1 Temporal-based, v2 produced beads as a by-product, v3 Python Gas Town, v4 the Go rewrite — "17 days, 75k lines of code, 2000 commits" at launch). Canonical repo `gastownhall/gastown`; MIT; created 2025-12-16; 17,869 stars; latest release v1.2.1 (2026-06-06); still maintained ("we're going to continue maintaining the O.G. Gas Town") but formally succeeded by Gas City.

### Architecture

Everything is beads. "In Gas Town, an agent *is* a Bead" — workers have persistent identities as pinned beads (an Agent Bead pointing at a Role Bead carrying priming instructions), sessions are the disposable part ("sessions are ephemeral; they are the 'cattle'"). The roles:

- **Overseer** — the human, with an identity and a mail inbox.
- **Mayor** — town-level coordinator agent the human talks to; files and slings work.
- **Crew** — long-lived, human-named per-rig agents for interactive work.
- **Polecats** — ephemeral per-rig workers spawned into swarms; produce Merge Requests, then are decommissioned.
- **Refinery** — per-rig merge-queue agent; Bors-style bisecting batch merges to main ("polecats never push directly to main"; the *agent* merges, not a human).
- **Witness** (per-rig) / **Deacon** (town-level patrol) / **Dogs** (Deacon's helpers) / **Boot** (a dog whose only job is checking the Deacon every 5 minutes) — a three-tier AI watchdog chain under a Go daemon heartbeat.

Propulsion is **GUPP** — "If there is work on your hook, YOU MUST RUN IT" — where a hook is a pinned bead per agent that work gets slung onto (`gt sling`). Because Claude Code often just waits for input anyway, GUPP is backstopped by `gt nudge`, a tmux send-keys hack, and the whole heartbeat hierarchy above. Workflow durability is **MEOW** (Molecular Expression of Work): Formulas (TOML workflow templates) are "cooked" into protomolecules and instantiated as **molecules** — chains of beads an agent walks step by step, surviving crashes and compactions; Yegge calls the resulting property Nondeterministic Idempotence ("the *outcome*... eventually finishes, 'guaranteed', as long as you keep throwing agents at it"). **Convoys** wrap slung work into trackable delivery units. **Seance** (`gt seance`) lets a fresh session literally `/resume` its dead predecessor in a subprocess and ask it questions. tmux is the UI; there is also a web dashboard, an OTel event/metric stream, and **Wasteland**, a DoltHub-federated cross-town work bounty board.

### Maturity, in Yegge's own words

The launch post's warning section is titled "WARNING DANGER CAUTION / GET THE F*** OUT / YOU WILL DIE" and includes: "the code base is under 3 weeks old... It's also 100% vibe coded"; "Do not use Gas Town if you care about money" (he needed a third Claude Max account within weeks); "It's very much a hands-on-the-wheel orchestration system"; "Work in Gas Town can be chaotic and sloppy... Some bugs get fixed 2 or 3 times... Other fixes get lost. It doesn't matter, because you are churning forward *relentlessly*"; and a stage-gate — if you don't already juggle 5-10 concurrent agents daily, "you will not be able to use Gas Town. You aren't ready yet." He also predicted its lifespan: "Gas Town itself may not live longer than 12 months, but the bones of Gas Town — the MEOW stack — may live on." Eight months later that is roughly what happened.

## C. Gas City (`gc`)

Gas City exists as a distinct, real project — this needs saying carefully because the Gas Town repo contains *both* eras of documentation. Older in-repo research docs (e.g. `docs/research/w-gc-004-agent-framework-survey.md`) describe Gas City as "the planned declarative layer on top of Gas Town... It doesn't exist yet as a standalone product," and `docs/agent-provider-integration.md` still calls its provider contract "forward-looking." Those documents predate February 2026. The repo `gastownhall/gascity` was created 2026-02-22, and Yegge's "Welcome to Gas City" (2026-04-24) announces v1.0.0. As of 2026-08-31 it is at v1.4.1 (2026-08-15), 1,206 stars, pushed the same day this was researched.

What it is: "It is Gas Town, but torn apart and rewritten from the ground up as an SDK for building your own dark factories... deconstructed the entire Gas Town stack into composable, declarative building blocks called 'packs'" — declarative `city.toml`, multiple runtime providers (tmux, subprocess, exec, ACP, Kubernetes, herdr), "a controller/supervisor loop that reconciles desired state to running state," and a stock "Gas Town pack" that reproduces the original as its default topology. Two facts reframe the whole stack: **Yegge did not write it** ("I did not write Gas City. It was created by Julian Knutsen and Chris Sells... I am only lightly affiliated with the code") and it is positioned as the disciplined successor ("Unlike Gas Town, which is an experiment run like a Wild West, Gas City is a rapidly maturing, enterprise-focused SDK"). Its sales pitch is de-SaaSing: agent packs as AI-native business-process automation, with the Dolt-versioned MEOW ledger as the audit story ("That's your SOC2 story, sitting right there in the database"). Beads remains the mandatory substrate (bd ≥ 1.0.0 and Dolt ≥ 2.1.0 for the default provider; a file-based fallback exists).

So the naming resolves as: **beads** = the data plane, **Gas Town** = the first (personal, chaotic) orchestrator on it, **Gas City** = the second (SDK-shaped, other-people-run) orchestrator on it, **Wasteland** = federation between installations. The docs domains (`beads.gascity.com`, `docs.gascityhall.com`, `gastownhall.ai` Discord) all belong to the same `gastownhall` org.

## What the sources do not answer

1. **No single-operator, single-worker evaluation exists anywhere in the stack.** Every design document assumes either many agents (Gas Town: 20-30; Gas City: "hundreds of concurrent workers in a city") or one human with many sessions. Beads' zero-conflict hash IDs, Dolt cell-level merge, claim atomicity, and cross-machine sync are all costs paid for coordination the Loop's one worker never needs. Whether `bd` is worth running with exactly one writer is not a question any source asks.
2. **Beads' trust model is unexamined.** Agents create issues, close issues, and write memories that get injected into every future session (`bd prime`). Nothing in the docs distinguishes operator-authored from agent-authored beads, and nothing gates dispatch on human authorship. The whole stack assumes the Overseer reads the feed; there is no equivalent of a Handover. Prompt-injection through the work source — the exact risk ADR 0003/0010 organize the Loop around — is never mentioned.
3. **Quality outcomes are asserted, not measured.** The MAKER Hanoi claim, "shockingly good performance," and the enterprise anecdotes are Yegge's own reports; the only quantified artifacts are throughput ones (LOC, commit counts, star counts). No source measures rework rate, merge-queue rejection rate, or how often the Refinery's agent-judged merges are wrong — and the launch post concedes "some bugs get fixed 2 or 3 times... other fixes get lost."
4. **Gas Town's maintenance future is vague.** "New maintainers onboarding" and "as long as people still need it" is the whole statement; the last release predates the Gas City v1.4 push by two months.
5. **What fraction of beads' 815k lines serves Gas Town rather than the tracker** is not documented. The `issues` table carries a dozen orchestration columns (`hook_bead`, `rig`, `agent_state`, `waiters`...) that a plain tracker user never touches; the coupling runs one way in the docs ("Gas Town is built on Beads. There is no 'alternate backend'") but the schema shows it also ran the other way.
6. **Medium posts were read via Wayback captures** (Cloudflare blocks this host); the 2026-08-11/2026-08-21 snapshots may lack Yegge's later edits.

## Fit against the Loop

**Gas Town/Gas City: inspiration, not adoption — confirmed.** Every organ of Gas Town exists to manage what parallelism and agent-authored intake create: the Refinery exists because swarms produce merge conflicts (one Run at a time produces none); Witness/Deacon/Dogs/Boot exist because 20-30 unattended agents stall in ways no human notices (the Loop's Termination Contract bounds one); convoys exist because work scatters across workers (a Run has an Owning Area); GUPP-plus-nudge exists because their agents idle between slings (the Loop launches a fresh Iteration that reads the Plan — GUPP is solved by construction). Two Gas Town ideas are worth stealing as *ideas* only: seance is evidence that "ask the predecessor" has value — the Progress Log already is the Loop's better-behaved version of it — and molecules/formulas (predeclared multi-step workflows as data an agent checks off) rhyme with Discipline Skills, and would only earn their complexity if a Run ever had to execute a long fixed ceremony like a release. Gas Town also directly contradicts two Loop invariants: its Refinery *merges to main on agent judgment* (vs Proposal-Only Output) and its agents author their own work items (vs Handover). Gas City changes none of this at one-worker scale; it is an SDK for building the thing the Loop deliberately is not.

**Beads is the serious comparison, and the verdict is: do not adopt, but take one idea.** Point by point against Plan + Progress Log + Journal:

- *Ready-work / dependency graph*: beads' `ready_issues` view is the Selector's Eligibility predicate in SQL. The Loop already computes this from native GitHub tracker edges, over a queue small enough for one operator to hold in his head. Equivalent capability, already owned.
- *Plan-file decay*: beads' founding problem — 605 decaying sibling plans — is a disease of *standing* plan files accumulated across many concurrent long-horizon efforts. The Loop is structurally immune: one Plan per Run, created by Seeding from an operator-authored issue, session-scoped, deleted when the Run's work ends. Yegge's evidence argues against persistent plan files, which the Loop already doesn't have; it does not argue against a per-Run Plan.
- *Cross-session memory* (`bd remember`, `bd prime`, compaction): solves fresh-context amnesia for agents that must resume an open-ended effort. The Loop's fresh context is handed exactly what it needs (Plan + Progress Log) for exactly one task; durable project knowledge belongs in the repo's docs and the tracker, both operator-reviewed. Injecting agent-written memories into every future session unreviewed is precisely the content-trust collapse ADR 0003 only permits because the operator authored the input — beads would reopen it.
- *Adoption cost*: a Dolt database inside the repo becomes de facto Executed-Path-adjacent state that model output writes unattended, plus a 815k-line fast-churning dependency (128 migrations in ten months, a schema-skew guard that exists because binaries and databases drift apart in the wild), for a queue of tens of issues. The Journal (Postgres, append-only, off the box's agent path) already provides the audit spine beads' events journal provides.
- *The one genuine gap beads exposes*: **discovered work dies with the Progress Log.** Beads' `discovered-from` edge and the "filed issue 397 and continued" behavior solve a real problem the Loop has: a Run that notices a broken test or a latent bug outside its Owning Area records it in a file that is deleted when the Run's work ends, and Proposal-Only Output forbids the Run from filing an issue itself. Today that knowledge survives only if the operator happens to read the Progress Log before deletion.

**Recommendation.** Do not adopt beads or any Gas-stack component. Instead, close the discovered-work gap inside the existing invariants: require the Run to carry a `## Discovered` section in the Progress Log, and have the Run Notification (or the Proposal body — both already inside Proposal-Only Output) surface those items verbatim to the operator, who authors real tracker issues from the ones he judges worth keeping. That preserves the Handover — the operator, not the model, remains the only author of work the Loop may be dispatched on — while borrowing the single insight in Yegge's stack that survives at one-worker scale: work an agent notices and cannot record durably is work the system will pay to rediscover.
